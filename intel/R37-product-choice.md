# R37 product choice: duplicate supplier invoice review

Decision recorded 2026-10-16. Build `duplicate-invoice-check`: a local, deterministic comparison of a supplied invoice-history batch. This is an implementation specification, not a claim that the feature has shipped or produced revenue.

## Ranked choice and evidence

1. **Duplicate supplier invoice review.** The existing three-way matcher explicitly states that saved reports do not detect repeated invoice references across checks. `bank-statement` deduplicates imported bank rows, not supplier bills; `recurring` warns about outgoing schedule-period duplicates. A separate supplied-history diagnostic fills that gap without inventing another alias. Current Oracle documentation describes supplier/type/amount/currency/date checks independently of the invoice number; older Oracle documentation specifically describes case-varied references and duplicate supplier names. These establish a real accounting control, not willingness to buy our product. [Oracle current documentation](https://docs.oracle.com/en/cloud/saas/financials/26a/fappp/how-can-i-find-duplicate-invoices-without-considering-the.html), [Oracle invoice audit documentation](https://docs.oracle.com/cd/A60725_05/html/comnls/us/ap/duplinv.htm).
2. **13-week cash forecast.** Useful but second: it needs explicit cash-timing assumptions, opening cash and handling of overdue items. The estate already forecasts recurring invoice revenue, although that is not cash. A direct competing MCP exposes a 13-week forecast from a connected Cash Runway account. A local forecast could still differentiate on privacy, but it introduces more assumptions before a buyer obtains dependable results. [Cash Runway's own MCP documentation](https://docs.cashrunway.ai/agent/mcp), [Australian government cash-flow guidance](https://business.gov.au/finance/cash-flow/set-up-a-cash-flow-statement).

A public NetSuite user reports a duplicate-number error where they cannot find a matching bill; replies describe separate subsidiaries and recycled references. This is qualitative evidence for review warnings and entity boundaries, not representative demand. A public invoice-triage project already implements a duplicate-reference check over MCP; do not claim this category is unique or unserved. [User question](https://www.reddit.com/r/Netsuite/comments/1ti01jb/invoice_number_exists_but_i_dont_actually_have_a/), [Project author's write-up](https://github.com/ajoys24/invoice-triage-copilot/blob/main/WRITEUP.md).

## Narrow acceptance contract

Suggested primary tool: `duplicate_invoice_check({entity_id, invoices, save?})`.

- One explicitly named legal entity per call; the caller must supply only that entity's records. `entity_id` is required and retained in the report. No cross-entity inference.
- `invoices`: 1–500 structured records. Each has a unique `record_id`, exact `supplier_id`, `document_type` (`invoice` or `credit_note`), `invoice_number`, `invoice_date` (`YYYY-MM-DD`), uppercase three-letter `currency`, and **positive integer** `total_minor` no greater than `Number.MAX_SAFE_INTEGER`. Credits use their own type with positive absolute value; do not net them against invoices. Optional `supplier_name` is display evidence only. No PDF/OCR, CSV dialect guessing, ERP access or payment execution in v1.
- IDs/references: 1–120 characters, no surrounding whitespace, controls or empty values; strict objects reject unknown fields. Dates must exist in the calendar. Duplicate record IDs invalidate the batch; they must not be silently deduplicated. The source record array remains intact.
- Compare only records with the **same exact supplier ID, same document type and same currency**. A different supplier ID is a different comparison scope even if its display name matches. Different currencies are distinct scopes; no conversion or cross-currency duplicate detection. The report must state these exclusions so a zero is not read as a universal clearance.
- Exact reference collision: identical raw invoice numbers in a comparison scope, irrespective of differing dates or positive amounts. Preserve amount/date differences as explicit evidence, not reasons to silently drop the collision.
- Normalized reference collision: distinct raw references whose conservative normalized keys match. Normalize ASCII `a`–`z` to uppercase and remove only ASCII spaces, `-`, `/` and `.`. Preserve leading zeros and every other character. Never convert `O` to `0`, strip arbitrary punctuation, remove accents or join vendors. An empty normalized key must not match another empty key. Return the key and transformation policy.
- Same-amount/same-date review: same exact positive `total_minor` and identical valid `invoice_date` in the comparison scope. This is a weak signal: recurring charges and separate legitimate invoices can satisfy it. The output must label it as a review candidate and show every source reference. No date-window or transitive near-date clustering in v1.
- Output candidate groups for each exact equality key, not every pair. Groups have at least two source records, one of the three rule codes, its scope/key and ordered source indices/record IDs. Use collision-safe tuple keys such as `JSON.stringify([supplier_id, document_type, currency, reference])`, never delimiter concatenation. Each input record belongs to at most one group per rule, so total membership is at most three times the input count. Order groups deterministically by rule then first source index. Source records are never dropped, merged or rewritten. Groups from different rules can overlap; never union them into a confirmed duplicate cluster or imply every record in a transitive union matches every other record.

Output: schema version, scope/policy, `review_required` or `no_candidates_in_supplied_data`, input count, comparison-scope count, candidate-group count, distinct flagged-record count, counts by rule, and ordered candidate groups. Every group references its complete source rows and exposes its raw/normalized key plus differing-date and differing-amount flags where relevant. Retain original records once in a source section; group records reference them rather than copying source values. No probability score, recoverable-money total or estimated savings. Groups overlap and their amounts cannot be summed as losses. A zero result means only that these rules found no candidates in these supplied records.

## Bounds, storage and payment

- A 500-record batch has at most 750 candidate groups and at most 1,500 group-member references (three equality rules; each emitted group needs at least two records). This is a formula bound, not a measured runtime result. An all-colliding batch emits at most three groups with 500 members each, not 124,750 pair expansions. Test complete source membership on that case.
- Respect the SDK's 10 MiB incoming-message ceiling. Set an encoded response budget at most 8 MiB. Return a bounded summary and a stable report/preview ID whenever the full result will not fit. Group pages must not hide member arrays larger than the page size: offer a group-members section indexed by group ID so every member is accessible in pages of at most 100. Never slice candidates while reporting the batch as complete.
- Free `report_page` exposes every group, every group member and every source row with explicit `total`, `offset`, `returned`, and `next_offset`; pages at most 100 records. Full evidence and CSV export are free. CSV escapes formula-like text; it returns text, not an arbitrary write path.
- Unsaved large diagnostics use two process-local previews, expiring after 30 minutes, as in the matcher. State expiry and restart behavior in the response. Re-running the same supplied input can recreate the diagnostic. A save-cap or filesystem failure must not suppress diagnostics or free paging.
- Free: 3 concurrent saved report slots. $19 one-time Pro: remove the report-count cap; $39 bundle includes it. All input, response and file-integrity limits apply equally. Do not withhold a safety check or source evidence. Saved reports are snapshots of supplied history, not an automatically growing accounting ledger.
- Saved JSON: atomic write, exclusive mutation lock, safe UUID lookup, no symlink ancestry, no caller-supplied export path; 64 MiB per saved report/read integrity ceiling. Store group source indices and reason codes rather than repeated source objects so the documented worst case remains practical. If the ceiling is exceeded, return an explicit save failure with complete diagnostic paging retained.
- Tools: primary diagnostic, report list/get/page/delete/CSV, license status/activate. No account/API key needed for free operation and no network in diagnostics. Use an independently testable pure core for a browser proof if the root chooses that distribution surface.

## Required adversarial cases

Exact raw duplicate; case/spacing/punctuation variation; reference collision with different amounts and dates; leading-zero difference preserved; `O`/`0` distinct; non-ASCII letters preserved; punctuation-only references produce no empty-key collision; identical references at different suppliers or currencies excluded; separate legal entities handled as separate calls; invoice versus credit excluded; legitimate recurring charges shown as weak candidates only when their date and amount exactly coincide; exact-date boundaries and leap days; malformed dates; decimals, zero/negative/unsafe money; duplicate record IDs; unknown fields; input order determinism; all members in each applicable group for an all-colliding 500-record batch; overlapping-group counts do not count invoices as unique duplicates; every page reconstructs the exact result without repeats/omissions; huge escaped strings respect the wire budget; saved-report-cap and filesystem failures preserve diagnostics; formula-safe CSV; concurrent saves/deletes; symlink and traversal rejection; offline valid/invalid Pro activation; actual stdio `tools/call` in standalone and office-proxy contexts.
