# R38 staged deployment adoption

Wrangler 4.80.0's strict direct deployment rejected the existing API-origin Worker before changing production. Removing `--strict` would discard the conflict stop. The supported alternative separates uploading an immutable Worker version from assigning it production traffic, with explicit configuration and ownership checks between those operations.

Cloudflare documents this split in [Deployment management](https://developers.cloudflare.com/workers/versions-and-deployments/deployment-management/) and the [Wrangler Worker commands](https://developers.cloudflare.com/workers/wrangler/commands/workers/). Versions preserve code, bindings and runtime settings; deployments choose traffic allocation. Routes, custom domains and cron triggers are separate, non-versioned trigger settings. This release does not invoke `triggers deploy`.

The installed source `/Users/mike/.npm-global/lib/node_modules/wrangler/wrangler-dist/cli.js` was inspected directly, not inferred from newer documentation. Version upload has an API-origin warning and confirmation, but does not activate traffic. Its noninteractive confirmation defaults to yes. It emits `Worker Version ID: <uuid>`. Upload sends `keepSecrets: true` and `bindings_inherit=strict`. `getMigrationsToUpload` returns no pending migration when the live migration tag equals the final configured tag. The subsequent version-deploy command creates the traffic deployment and then synchronizes explicitly configured non-versioned settings such as observability. It does not deploy routes or cron schedules.

The newer [gradual deployment documentation](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/) notes that versions of Wrangler before 4.131.0 may return error 10211 for Durable Object migrations. No Durable Object lifecycle change is requested here: the existing `FULFILLMENT` class and `fulfillment_state_v1` tag are retained. This inspection establishes the intended no-migration path, not proof that a live version upload will succeed. If Cloudflare refuses the upload, the wrapper stops without changing traffic or attempting rollback. A staged upload still requires live verification by the coordinator.

The native read-only baseline in [r38_deployment_adoption_baseline.json](../data/r38_deployment_adoption_baseline.json) confirms the current billing version, a 400 ms CPU limit, the existing migration tag, eleven binding names/types, a five-minute cron, enabled logs and traces, and zero configured tail consumers. Its full version configuration is hashed in memory; no binding values or secrets are exported. The installed Wrangler source hash and version are recorded there. The remote Worker separately retains its already measured 1,500 ms CPU limit in the parent's configuration change.

The revised supported billing wrapper performs these steps:

1. Read the approved pin and sole active deployment, requiring the active version to equal that pin. Record the tested source hash and approved version's configuration.
2. Run the unchanged local preflight, including the strict, key-independent Wrangler dry run. Recheck source hash, active deployment identity and remote pin.
3. Run `wrangler versions upload`. Require exactly one explicit uploaded version ID, then inspect that exact version. Refuse any difference in binding identities or values, Durable Object namespaces, migration state, compatibility settings, CPU limits or exported handler shape. Differences in code hashes, creation metadata and version IDs are expected and excluded from the configuration comparison.
4. Before traffic changes, recheck the source hash, the original deployment ID/version and the original remote pin. Activate only the exact staged UUID at 100% with `wrangler versions deploy <uuid>@100% --yes`.
5. Refresh the authoritative active deployment even when the activation CLI throws. A timeout or failure after its API request is not evidence that traffic stayed on the earlier version.
6. Retain the existing source checks, live GET-to-Stripe intent-page guard, deployment ownership checks and local/remote approved-version pin update. The CLI still accepts no bypass flags.

Recovery distinguishes stages. An upload or configuration-check failure before activation leaves traffic untouched and never triggers rollback. A failed activation that is authoritatively observed to have left the original deployment unchanged also needs no rollback. If the staged version is observed as the sole active deployment, rollback remains subject to the original deployment-ID/version and unchanged-pin guards, refreshed immediately before rollback. If the activation result cannot be observed, or the observed deployment belongs to another version, recovery is manual. An ambiguous final remote-pin write remains manual because KV propagation can conceal a committed write. These are best-effort ownership checks, not an atomic compare-and-swap against concurrent operators.

`executeRelease` accepts effect implementations for offline tests; the production CLI supplies only the fixed Wrangler and gate commands. The tests exercise success ordering and real failure transitions: failed preflight, changed source before/after upload and activation, malformed/ambiguous upload output, changed live deployment or pin, changed staged namespace/CPU/migration/handler configuration, activation failure before and after a committed traffic change, unavailable activation observation, failed live verification and ambiguous final pin writes. Configuration error messages reveal field groups, not private variable values. The source-hash fixture now checks `lsof` and records its size/path before deletion.

Local execution is guarded by the owner's 20 GB disk floor and the actual `/Users/mike/bin/buildslot`. At initial inspection `df -g /System/Volumes/Data` reported 19 GB; the required coldstore plan reported zero candidates. No build or test was started below that floor. The bounded buildslot wait and eventual test outcome are retained in [r38_deployment_adoption_tests.tap](../data/r38_deployment_adoption_tests.tap); consult [the current receipt](../data/r38_deployment_adoption.json) before treating the change as validated. CI's strict dry run and normal production gates must pass before live adoption.

No version upload, traffic activation, trigger update, secret update, payment or email was performed by this review. The coordinator owns live adoption, subsequent configuration comparison and postdeploy verification.
