The finding that matters

The Buy button does not sell anything

Traced end to end on the live origin: GET /buy/bundle renders a form → POST /buy/bundle answers 303 → /s/bundle → and /s/bundle contains exactly one action, an email subscribe box posting to /api/subscribe, which returns {"ok":true,"status":"subscribed"}.

Correction, measured this session. An earlier probe in this same session concluded that no checkout existed. That was wrong: it was a curl request, and the worker classifies curl as scripted and redirects it to the product page (x-mcp-buy: scripted-ua-no-session). Driving the real buyer path — browser UA, same-origin Origin, Sec-Fetch-Mode: navigate, body intent=checkout — returns 303 to checkout.stripe.com/c/pay/cs_live_…, and that page serves HTTP 200. The worker holds a live key and the /success and webhook fulfilment paths are implemented.

Consequence: the plumbing is not the problem. 334 buy clicks produced 100 checkout confirmations and zero payments, and 2,780 open/expired sessions in one week carried no PaymentIntent — automation crossing the guard, i.e. our own probes, not buyers. With 0 of 299 URLs indexed there is no population from which to compute a conversion rate. Optimising conversion at this traffic level is arithmetic on zero; distribution is the only lever.

Traffic is not zero — it is 188,640 requests a day and none of it is human

Cloudflare GraphQL, 24 h, host mcp.zovo.one: 188,640 requests, of which 23,764 were HTTP 429 — 12.6% of everything the estate served. The user-agent split says who is asking: SentinelOracle 57.5k, mcpbeat 42.9k, AgentRankProbe 9.6k, rokmcp-collector 8.4k, alalanet-prober 2.7k, and real MCP clients — node 13.8k, python-httpx 4.3k. Human browser traffic is approximately zero.

The 429s were our own defect, and they cost us placement. A directory health check walks every registered endpoint; one sweep of the catalogue is 58 calls, and probes re-run hourly. The discovery tenant was keyed on IP alone with a 120/hour ceiling, so a probe throttled itself after two sweeps — and crawlers sharing a cloud address ate each other's budget. Directories score availability, so a 429 from us reads as "server is not responding".

Fixed in commit da91b8eb, deployed as 40cd4501: discovery is now keyed by user-agent family and IP, ceiling 120 → 1500. Proven live, both directions: 150 calls from one UA → 150 × 200, zero 429 (previously request 121 failed); 1,560 calls → 1,559 × 200; and an anonymous tools/call still returns 401, so the data path did not loosen.

Then the production number moved. Hourly 429 share on mcp.zovo.one, same day, before and after the deploy at 14:00 UTC: 10.1%, 12.4%, 9.6%, 11.4%, 7.5%, then 0.0%. Total requests held at roughly 10,000 an hour across every bucket, so this is not a drop in load — the throttling stopped while traffic stayed flat.

Search visibility, measured per URL

2 of 299 URLs are indexed: this is the whole traffic problem, in one number

Every URL in the sitemap was queried through Google's URL Inspection API on 2026-11-06 (not inferred from a sitemap field Google has deprecated). The result is three populations, and they need three different remedies:

  • 2 indexed - the home page and one endpoint. These rank for nothing yet; they are simply the only documents Google has accepted.
  • 101 discovered, not indexed - Google knows the URL exists, crawled or queued it, and declined to index it. That is a quality/authority judgement, not a discovery failure.
  • 196 unknown to Google - never crawled at all, despite the sitemap being downloaded with zero errors. On a domain with no inbound links, a sitemap is a suggestion Google is free to decline.

Defect found and fixed this session. The sitemap carried 47 /mcp/<id> URLs. Measured with curl, those answer application/json - the JSON-RPC descriptor, no <title>, nothing to rank. On a domain that is 196 URLs short of being crawled, 47 of 299 crawl slots were being spent on non-pages. The sitemap is now 253 URLs, zero JSON endpoints (58 /s/ pages, 140 guides, 37 compare, 8 setup, 3 suites, indexes; /mcp/connect stays because it is HTML). Deployed as mcp-billing 6eebdbdb through the gated release path and re-measured live: 253 <loc>, 0 JSON endpoints.

IndexNow submitted 253 URLs, 0 rejected (Bing, Yandex, Seznam, Naver - one 200 per batch). Google is not in IndexNow; that channel is the only one that answers a low-authority domain immediately, and Bing's index feeds several LLM search surfaces where developers actually look for MCP servers.

The honest read: indexation here is authority-limited, not structure-limited. Fewer junk URLs and a fresh ping are hygiene; they do not manufacture demand for a domain nobody links to. Traffic stays at zero until the estate appears where developers search - the registries - which is a placement problem, not a content problem.
